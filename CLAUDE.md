# About this project

This is Aman's public personal website — a personal portfolio/homepage, not a work project. It's hosted on GitHub Pages and built with plain HTML and CSS only. No frameworks, no build tools, no JavaScript bundlers — keep it that way unless Aman explicitly asks to add something.

## Who you're working with

Aman is a product manager, not a software engineer. He's new to coding. When explaining things:
- Use plain language, not jargon. If you have to use a technical term (e.g. "commit," "deploy," "CSS selector"), briefly say what it means.
- Work in small steps. Make one change, explain it, confirm it looks right, then move to the next — don't batch up a pile of unrelated changes.
- Explain *why* a change works, not just *what* it does, so he's building understanding over time.

## Safety rules

- **Never delete files, sections of content, or git history without asking first and explaining what will be lost.** This applies even to things that look like dead code or unused files.
- Before any destructive git operation (reset, force push, etc.), stop and check with Aman.
- This is a public site — assume anything committed is visible to anyone, forever (GitHub history included). When in doubt about whether something is safe to publish, ask rather than guess.

## Content rules

These apply to any text, images, or data added to the site:

1. **Only public information.** Nothing confidential, internal, or employer-proprietary. If a fact isn't already public elsewhere, don't publish it here.
2. **No personal contact details.** No phone number, no home address. (A public professional email or social/LinkedIn link is fine if Aman provides it.)
3. **No confidential employer details.** Don't describe internal processes, unreleased plans, proprietary metrics, or anything not already publicly disclosed by the employer.

### Wisk-specific terminology

Aman works at Wisk Aeronautics (or similar context) — when writing about Wisk's autonomy system:
- It is **deterministic, certifiable software** — never describe it as "AI," "artificial intelligence," or "machine learning." This is a hard rule, not a stylistic preference.
- **MR&Os are requirements**, not a process. Don't describe them as a workflow, procedure, or process step.

If a draft is ambiguous about either of these, flag it and ask rather than guessing at phrasing.

## Working style

- Since this is plain HTML/CSS, changes can be previewed by just opening the HTML file in a browser — no server needed unless relative paths require one. Suggest Aman open the file locally to check a change before it's considered done.
- Keep the site's structure simple and readable — this is a portfolio site, not an app. Favor clarity over cleverness in both code and content.
